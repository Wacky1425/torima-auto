# Torima Auto v3.4 — HOME紫ボタン原因切り分けパッチ

## なぜHOMEだけ効かないか
Wチャンスは文字付きのACTION_CLICK対象だが、HOMEは大きな無名ViewGroupを座標ジェスチャーで押していた。実際には押していても遷移判定がUNKNOWNへ変わる場合もある。さらに、記録・自動操作バー（Accessibility Overlay）がHOMEのタップ座標(例:514,1264)の上に重なると、アプリではなくバーがタッチを受け取る可能性がある。

## 仮説と比較方法

| 仮説 | 検証 | 結果の見方 |
| --- | --- | --- |
| 1. 自分の記録バーがタップを横取り | 毎回、記録バーをFLAG_NOT_TOUCHABLEにして220ms後に入力。事前にバー矩形との重なりを記録 | この版で成功、以前は不成功なら強い手掛かり |
| 2. タップ座標のずれ | 学習座標、矩形中心、右寄り59.3%をそれぞれ検証 | 位置による差が分かる |
| 3. GestureがViewのクリックに変換されない | ボタン自身のACTION_CLICKと学習座標ジェスチャーを比較 | ACTION_CLICKだけ効くならイベント経路の違い |
| 4. 子ノードではなく親にクリックリスナー | 親のACTION_CLICK（親が小さくクリック可能な場合のみ） | 親だけ成功すれば対象ノードの違い |
| 5. Gestureの長さ | 110/240/520/300msを比較 | 時間依存を確認するための対照群 |
| 6. 別のウィンドウが重なっている | 全アクセス可能ウィンドウのtype/layer/active/bounds/座標重なりを記録 | HOME上の他ダイアログ・オーバーレイを確認 |
| 7. タップ時点ではUIが押せない | 送る直前にROOTを再取得。clickable/enabled/visibleを記録 | 送信前にHOMEでなくなれば旧座標でタップしない |
| 8. OSではジェスチャー成功だがアプリがクリックと認識していない | gesture completedとTYPE_VIEW_CLICKEDを別々に記録 | Androidへの送信とアプリの反応を区別 |
| 9. 広告に移行したのにHOME失敗と誤判定 | 各入力後2.45秒の画面種別/ノード数を記録し、before/after画像も保存 | 画面変化≠広告の回収成功を区別 |
| 10. 別アプリやGoogle Playへ遷移 | 前面パッケージとウィンドウをチェック | クリックが外部へ遷移させた場合も分かる |

## 7種類の入力（最大約85秒、無制限リトライはしない）
1. 学習済み座標を110msでタップ（記録バー非タッチ化）
2. 紫ボタン自身のACCESSIBILITY ACTION_CLICK
3. 紫ボタンの狭い、押せる親ノードのACTION_CLICK（全画面親は禁止）
4. 紫ボタンの幾何学的中心を110msでタップ
5. 学習済み座標を240msでタップ
6. 学習済み座標を520msでタップ
7. 右寄りの位置を300msでタップ

各方式の間は7秒以上空け、毎回**最新**のHOMEと紫ボタンを再判定する。画面が切り替わったら、追加のHOMEタップはせず画面遷移を調べる。

## 実行
1. HOMEの紫ボタンを押せる状態にして、Torima Autoで「記録・自動操作バーを表示」
2. 記録バーの「▶開始」でタンク動画回収を開始
3. HOMEから広告に進めたか、または7方式が尽きるまで待つ
4. アプリの「操作履歴をコピー」を共有。JSON内 `type=home_experiment` は `before` / `window_layers` / `overlay` / `dispatch` / `gesture_completed` / `app_click_event` / `after_2s` / `screen_transition` の順で調査
5. 画面上の差を確かめたい場合は「画像診断をZIPで共有」。最初の10枚程度が保存され、画像は手動共有まで外部に出ない

## 注意
- 実際のトリマ端末での成功/失敗はこのパッチのビルドだけでは判定できない。
- ACCESSIBILITYのCLICKイベントは広告表示開始の確証ではない。実際の残回数・次画面と照合する。
- 自動操作に対するOS・アプリ側の非公開な制限は、ログから疑うことはできても解除できる保証はない。
- 意図しないクリック連打を避けるため、全画面を覆う親や無関係な座標にはタップしない。
