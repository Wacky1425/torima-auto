# 新チャットB/C/D/...：新しいポイ活アプリ開発テンプレート

## 目的
トリマの開発を止めずに**1アプリにつき1チャット・1ブランチ・1独立APK**で自動回収を実装する。新アプリの数は2つ以上、将来何個になっても同じ方式を使う。

## 最初にユーザーに確認する情報
- アプリ正式名：`<app-name>`
- 開発用slug：`<slug>`（例：lowercase英数字とハイフン。決まるまではファイルを勝手に`app2`等と命名しない）
- Androidの対象packageName：`<target-package>`（不明なら実機スクショ／Android設定／診断から確定。推測だけで決定しない）
- 自動化する具体的な回収対象：ボタン、回数表示、タブ、報酬獲得画面
- 画面遷移、広告・ガチャ・取り消し・購入・広告制約
- 回収の**完了証拠**：0件表示、灰色ボタン、完了メッセージ等（押した事実だけでは不十分）
- ユーザーが手動で押す順番と、問題時の診断方法

質問は本当に不可欠なものだけ。スクショを受け取ったら手元の仕様として整理する。端末とAndroid権限の制約、利用規約を考慮。

## 開発ブランチとモジュール
- ブランチ：`dev/app-<slug>`。このブランチがまだなければ、統合担当が最新安定基準から作成する（チャット側で勝手にmainをpushしない）。
- ソースの主な所有領域：`apps/<slug>/`。個別の`applicationId`、`targetPackageName`、AccessibilityService、UIと学習ルールを設定。
- 旧Torima`app/`および`AutoFlow.kt`をコピーしてそのまま改造しない。特に`jp.co.incrementp.milemobile`、トリマのガチャ文字列や赤丸座標を新アプリへ持ち込まない。
- `settings.gradle.kts`に新モジュールを追加する必要があれば、まず統合担当へ依頼。急ぎで自分のブランチへ一行追加した場合は差分を統合担当に明記し、mainへ勝手に反映しない。
- `common/`は統合担当が所有する。共通化候補の抽出・安全性改善はPRまたは提案として渡す。
- リソース、FileProvider authority、アプリラベル、ステータス表示、診断ZIPには`<slug>`を用いる。ユーザーがどのテストAPKか分かるようにする。
- 統合版のAccessibilityServiceと別々に操作しない。実機テスト中は**そのアプリ用のサービスだけ**を有効にする。

## 第1実装の最小ゴール
1. Androidの独立APKをビルドしてスマホへ導入。Torimaとは**別アプリとして共存**させる。
2. 対象アプリの現在のpackageName／ノード数／画面名を取り、対象外アプリは触らない。
3. 1種類の報酬回収を「開始・停止・進捗・完了の根拠」で動かす。広告・ガチャ・外部Play遷移には安全な制御と上限を設定。
4. 押せなかったとき、スクショ・ノード情報・状態・直前操作を**診断ZIP1個**で確認できるようにする。
5. 安定動作を実機で確認するまで、大規模な画像学習・大量画面をいっぺんに追加しない。
6. 単独APKが動いてから、使い回し可能なインターフェースとテストを統合チャットへ提案。

## 推奨タスク定義（各アプリで作る）
```text
task_id: <slug>.<reward_kind>
target_package: <実機で確認>
start_screen: <どの画面から>
navigation: <画面別遷移>
action: <何を押す>
expected_result: <何が変わる>
completion_evidence: <実際の表示を二度確認する条件>
timeout/retry_limit: <有限にする>
unsafe_actions: 購入・シェア・券消費等
failure_diagnostic: 1 ZIP
```

## ビルド・デバッグ
開発中は`dev/app-<slug>`にコミットし、[開発版ビルド手順](BRANCH_AND_RELEASE_RULES.md)で`apps:<slug>`のdebug APKを取る。Debug署名が毎回変わる場合があるため、上書きテスト用署名の整備は統合担当と協議。Actionsのビルドが通っても「実機動作OK」と主張しない。**公開正式Releaseは統合チャットのみ**。

## チャットの終了時に統合へ渡す情報
アプリ名／slug／target packageName／applicationId／ブランチ／コミットSHA／動作するタスク／実機検証結果／使用した共通候補／未解決の画面／テスト済みAPKの入手先／統合側へ求める変更を箇条書きで[STATUS.md](STATUS.md)へ追加する。
