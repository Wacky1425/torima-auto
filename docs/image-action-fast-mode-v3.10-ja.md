# Torima Auto v3.10 — 高速実験 / 画像認識を実際の操作へ接続

## 解析した入力（v3.9診断ZIP）
- 24枚のスクリーンショットが保存されていた。特に楽天広告の右上×（約x=978,y=272）と黒背景広告の右上×（約x=1030,y=160）が写っていた。これらは通常のAndroidノード判定だけでは操作できないことがある。
- 既存の画像解析の候補は下側の模様に多数反応し、明確な2つの右上×を見逃していた。元画像を540px幅に縮小し、白い斜め4方向の明るさを周囲の縦横背景と比較する検出器を試した結果、当該2枚が検出され、確認した他の22枚では動作候補を返さなかった。これは保存済みサンプルに対する検証であり、未知の広告すべての保証ではない。
- 操作ログには16:24:30・16:24:50（ログの元時刻タイムゾーン）など広告Close後に4秒の固定静穏期間が複数回記録されていた。その後も追加の安定待ち、18秒の同一画面クールダウンが存在した。
- ノード情報だけでは広告を識別できない（2〜7件など）画面があり、スクリーンショット解析を操作の判断に直接組み込む必要がある。
- v3.7の「トリマのアプリ情報 → 強制停止確認 → 再起動要求 → トリマ前面復帰」はログ上成功。強制停止UIを押した結果であって内部のプロセス終了の直接証明ではない。

## 変更点
1. 「高速実験：広告終了後の保護・待機をOFF」をアプリ設定に追加、初期ON。既存の固定4秒静穏期間、さらにその先の広告後安定待機、90秒の復帰状態保留を無効化する。従来の挙動へ戻すにはOFF。
2. 類似する広告Close操作の同一画面18秒連打抑制を、高速実験中のみ2.5秒に短縮。別の画面へ変化したかどうかの確認と、同じ画面への無制限連打の禁止は残す。
3. ノードがなくても、動画広告の入場経路（スキップ券の「使わない」、動画を見て再チャレンジ）が確認されていれば、Androidのスクリーンショットから右上の白いXを探す。
4. 画像候補は連続2枚で同じ位置であることを確認してから操作する。単なる写真保存や候補抽出だけでは押さない。画像上のXはUIノードがない広告でもタップ対象にする。
5. 画像検出を実行したときは、画面の状態表示に画像由来の判定根拠（位置、SDKの証拠、動画へ入った経路）を残す。
6. 保存画像のindex.jsonには今後PixelAdCloseDetectorの候補座標とスコアも記録する。

## 注意点
- 速度優先のため、広告を閉じた直後のガチャ遷移画面を取り違えるリスクがあり、これがテスト目的。ONの状態で誤キャンセルが再発したらOFFに戻して、一括診断ZIPを共有する。
- 本パッチは「広告終了後の保護」の切り替え。ガチャカード画面や報酬画面そのものに対する固有の操作判定、シェア・課金・スキップ券消費の禁止は変更しない。
- 画像検出は白い×（今回の実画像で確認できた2種類）に集中する。黒い×や広告内テキストの完全OCRを実装したわけではない。
- Androidの画面キャプチャを使うが端末外への自動送信は行わない。従来通り一括診断ZIPだけをユーザー自身が共有する。

## 試験
v3.10を既存のアプリに上書きインストール。高速実験は最初からON。通常の「▶開始」でトリマのHOMEから操作し、白い×のある広告を表示したら、自動の画像検出・操作が行われるか確認する。成功しない場合は「診断をまとめて共有（ZIP 1個）」で今回と同様に共有するだけでよい。
